# Contributing

Contributions of all kinds are welcome: bug reports, feature requests,
documentation and pull requests.

**The most helpful thing right now is real-world testing.** If you try
MRTKLIB Web UI with your own receiver or data set and something does not work
as expected, please open an issue. You do not need a fix: a clear description
of what happened is enough.

## Opening an issue

When reporting a bug, please include:

- Which screen or feature was affected
- What you expected to happen
- What actually happened
- Browser and OS (and the Docker version if relevant)
- Any error messages from the browser console or the Docker logs

For a feature request, a short description of the use case helps more than a
specific implementation.

## Pull requests

For small fixes (typos, obvious bugs), open a PR directly. For larger
changes, please open an issue first to discuss the approach; this avoids
duplicated effort. PRs target the `develop` branch.

- Python: PEP 8, type hints throughout
- TypeScript: strict mode, functional components
- Commits: conventional commits (`feat:`, `fix:`, `docs:`)
- Do not modify MRTKLIB source code in this repository

## Development setup

### Backend

Python 3.12 and [uv](https://docs.astral.sh/uv/):

```bash
uv sync
uv run uvicorn mrtklib_web_ui.main:app --reload --host 0.0.0.0 --port 8000
uv run pytest      # backend tests (pytest is in the dev dependency group)
```

The backend runs `mrtk`, so a local MRTKLIB build on the `PATH` is needed for
the features that start processes. The Docker image has it built in.

> **Note:** QC Preview is temporarily disabled (the button is greyed out and
> `/api/obs-qc/analyze` returns 503) until it is integrated with MRTKLIB QC.

### Frontend

```bash
cd frontend
npm install
npm run dev        # http://localhost:5173, proxies API requests to :8000
npm test           # Vitest + Testing Library
npm run lint
```

### Docker

```bash
docker compose up --build                  # http://localhost:8080
scripts/docker_smoke_test.sh IMAGE         # what CI runs on the built image
```

### Documentation site

The site at <https://h-shiono.github.io/mrtklib-docker-ui/> is built from
`docs/` with MkDocs Material (`mkdocs.yml`), in the `docs` dependency group:

```bash
uv run --group docs mkdocs serve           # http://127.0.0.1:8000
uv run --group docs mkdocs build --strict  # what CI runs
```

`.github/workflows/docs.yml` publishes it on every push to `main`, so the
site shows the latest release; pages written on `develop` appear with the
next release. CI builds the site with `--strict` on every PR, which fails on a
broken link or a page missing from the nav. Option meanings belong in the
[MRTKLIB documentation](https://h-shiono.github.io/MRTKLIB/): link to it
instead of copying it. `docs/reference/config-coverage.md` is generated by
`scripts/gen_config_coverage.py`; do not edit it by hand.

## Architecture

- **Backend**: Python, FastAPI, Pydantic v2; `asyncio.subprocess` starts the
  `mrtk` processes, and WebSockets stream their logs and status.
- **Frontend**: React 19 + TypeScript, Vite, Mantine v8; Chart.js, uPlot and
  Recharts for charts, Leaflet for maps; IBM Plex Sans + IBM Plex Mono.
  `DESIGN.md` is the design system.
- **Deployment**: a multi-stage Docker build compiles MRTKLIB (the unified
  `mrtk` binary, version pinned in `.mrtklib-version`) with CMake, builds the
  frontend, and serves both from one container. Volumes: `/workspace`
  (read-write), `/data` (read-only).

## Releases and images

### Tag → image mapping

The `publish-docker.yml` workflow is the only thing that pushes to GHCR and
Docker Hub. It runs on two events:

| Trigger | Resulting tags (per registry) |
|---|---|
| `git push origin vX.Y.Z[-suffix]` | `X.Y.Z[-suffix]`, `sha-<7-char>`. For non-prerelease tags also `X.Y`, `X`, `latest`. |
| `gh workflow run publish-docker.yml --ref <branch>` | `dev-<branch>` only. Repeated runs **overwrite the same tag** in place; nothing accumulates. |

So the recommended dev cycle is `gh workflow run --ref my-branch` →
`docker pull ...:dev-my-branch`. Cutting a release is the only way to mint a
new long-lived tag.

### Release notes

From v0.5.0 on, every release, patches included, gets a page
`docs/releases/release-notes-vX.Y.Z.md` and an entry in the Releases section
of `mkdocs.yml`. A minor release uses the same text for its GitHub Release.
The image tag in the README and in `docs/getting-started/install.md` follows
the release.

### Cleaning up GHCR safely

**Do not bulk-delete "untagged" entries** in the GHCR Versions view.
Multi-arch images (`linux/amd64` + `linux/arm64`) live as a tagged manifest
list that *references* per-architecture manifests, which appear as untagged
digests. Deleting those breaks `docker pull` for that platform with
`manifest unknown`.

Safe order if the registry needs a tidy-up:

1. Delete `dev-*` or stale `sha-*` entries that have a tag. The platform
   manifests they reference then become true orphans.
2. Wait briefly (or refresh the view), and only then delete the now
   unreferenced untagged digests.
3. If a release tag does break, `git push --delete origin vX.Y.Z` followed by
   `git push origin vX.Y.Z` re-runs the workflow and restores the manifest
   list. The GitHub Release object re-attaches automatically.

The same rule applies to Docker Hub, which is just slower to show orphans in
its UI.
